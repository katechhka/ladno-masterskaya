# Ладно — мастерская ручных открытий

Портфолио-проект вымышленной творческой мастерской в Туле. HTML, Stylus, jQuery, ES-модули и Vite; серверная основа — Node.js и SQLite.

**Сайт опубликован: https://ladno-masterskaya.vercel.app/.** Админка: https://ladno-masterskaya.vercel.app/admin/. База — Turso Cloud, свои фотографии — Vercel Blob, Telegram — защищённый webhook. Программы, цены, фото и расписание меняются без сборки. Проверены настоящая облачная запись, конкуренция за места, отмена/отзыв, сохранность после нового релиза и копия с восстановлением. Полный локальный прогон: 60 тестов и пять браузерных наборов. Дизайн Unbounded / Onest и все 24 исходных сгенерированных изображения сохранены. [Актуальная инструкция Vercel](docs/CLOUD.md), [этапы](docs/PROGRESS.md).

Для хозяйки: [управление занятиями, фотографиями, ценами и расписанием](docs/ADMIN.md); отдельный облачный пароль — в закрытом локальном `storage/cloud-admin-access.txt`. Для разработчика: [Vercel и облачные копии](docs/CLOUD.md), [локальные копии](docs/BACKUP.md), [Telegram](docs/TELEGRAM.md). Готовый текст кейса: [описание для портфолио](docs/PORTFOLIO.md). Следующие разделы описывают локальный серверный вариант; его база отделена от опубликованной.

Она работает без Vercel и не создаёт брони. [Публикация на GitHub Pages](docs/GITHUB-PAGES.md).

GitHub: [katechhka/ladno-masterskaya](https://github.com/katechhka/ladno-masterskaya). Репозиторий публичный с разрешения владельца для публикации демоверсии на GitHub Pages.

Репозиторий содержит исходный код, демонстрационный каталог, сгенерированные изображения, локальные шрифты с лицензиями, PDF, тесты и инструкции. Рабочие базы, бронирования, загруженные через админку фотографии, резервные копии, пароли, `.env*` с секретами и настройки подключения Vercel в него не входят. `.env.example` содержит только пример настройки без ключей. После клонирования создайте собственную базу и доступ владельца по инструкции ниже; доступ к опубликованной базе не передаётся вместе с исходниками.

Отчёты проверок и скриншоты, упомянутые в документации, создаются локально командами проверки и не версионируются. Оригиналы сгенерированных иллюстраций и подготовленные изображения сайта включены. Перед коммитом проверяйте состав изменений; не добавляйте исключённые файлы принудительно. Публикация исходников сама по себе не запускает развёртывание на Vercel.

## Установка

Требуется Node.js ветки 22 начиная с 22.12. Проверено окружение 22.21.0; ветка закреплена также для Vercel. Установка `better-sqlite3` использует нативный модуль: при отсутствии подходящего готового бинарника потребуются инструменты сборки C++.

```sh
npm ci
npm run db:seed
npm run admin:setup
```

Lock-файл включён: используйте `npm ci` для воспроизводимой установки. Кеш npm локализован в `.cache/npm` внутри проекта.

## База и расписание

При необходимости скопируйте `.env.example` в `.env`. Команды базы читают этот файл. Путь базы по умолчанию: `storage/ladno.sqlite`, вне публичных файлов.

```sh
npm run db:migrate
npm run db:seed
```

Первое наполнение создаёт шесть недель относительно текущей московской даты, повторное не удаляет существующие сеансы и брони и не сдвигает опорную дату. Скрипты не печатают контактные данные.

API записи работает в том же процессе, что Vite или production-сервер. Для проверки используйте только вымышленные контакты. Доступность читается из общей SQLite-базы; запрос записи проверяет цену и остаток внутри транзакции.

Главная, расписание и запись читают `/api/catalog` и `/api/sessions`. Контакты, номера броней и токены в публичный ответ не входят. Остаток — вместимость минус участники подтверждённых броней. Все подписи дат используют Europe/Moscow.

Служебный публичный снимок можно экспортировать отдельно; интерфейс записи его не использует:

```sh
npm run schedule:export
```

`public/data/` — генерируемый каталог, исключённый из Git. Перед первым запуском или сборкой выполните `npm run db:seed`. Статического хостинга недостаточно: нужен Node.js-сервер с постоянным диском для SQLite.

## Редактирование

Для хозяйки: откройте `/admin/`. При первом запуске `npm run admin:setup` создаёт владельца `owner` со случайным паролем и сохраняет доступ в закрытый локальный файл `storage/admin-access.txt`. Сохраните пароль в менеджере паролей и удалите файл. Не публикуйте его. Повторная команда сохраняет существующий доступ; явный сброс: `npm run admin:setup -- --reset`, при этом завершаются все сеансы входа.

В админке можно создавать и редактировать программы, цены и галереи, архивировать программы, создавать сеансы с повторениями, переносить или отменять занятия, закрывать запись, просматривать контакты и отменять отдельные брони. Изменения сохраняются в SQLite и видны сразу. Отмена и перенос с участниками требуют подтверждения; участникам нужно сообщить лично. Пошаговая инструкция: [docs/ADMIN.md](docs/ADMIN.md).

Для разработчика:

- Рабочие программы: таблица `workshop_programs` в SQLite. `data/workshops.json` — исходное демонстрационное наполнение; после первого импорта его изменение не перезаписывает правки хозяйки.
- Преподаватели: `data/teachers.json`; связь через `teacherId`.
- Тексты, направления, FAQ, правила: `data/site.json`.
- Общая разметка: `src/partials/`; исходные шаблоны: `src/pages/`.
- Стили: `src/styles/`; JavaScript: `src/scripts/`.

Изменение шаблонов, стилей, скриптов и общих текстов требует сборки и перезапуска. Редактирование программ и расписания через админку этого не требует. Не редактируйте `dist/` и `.generated/` вручную.

Архитектура: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Сервер и защита брони: [docs/STAGE-4.md](docs/STAGE-4.md). Развёртывание с постоянной базой и HTTPS: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). Управление расписанием: [docs/ADMIN.md](docs/ADMIN.md).

## Запуск собранного сайта с API

Расширенная итоговая приёмка через локальный HTTPS-прокси:

```sh
npm run build
npm run acceptance:check
```

Проверяет настоящий production-процесс, защищённую cookie входа, CSRF/Origin, сохранение цены и фото после перезапуска, старую/новую сумму брони, отзыв согласия, PDF и футер на четырёх размерах. Создаёт только временный самоподписанный сертификат средствами Node.js; системное доверие не меняет. Для запуска нужен установленный Chrome. Рабочие данные не используются. Отчёт: `docs/acceptance-check.json`, подробности: [docs/STAGE-10.md](docs/STAGE-10.md). Публичное размещение этим тестом не подтверждается.

Проверка production-режима на изолированной файловой базе:

```sh
npm run build
npm run production:check
```

Используется настоящий `server/index.mjs`, включены ограничения запросов и production-заголовки. Скрипт проверяет прямые адреса, бронирование и отмену в Chrome на 1440 и 360 px, перезапуски процесса, закрытый доступ к данным и отсутствие ошибок консоли. Рабочая база и `.env` не меняются. Отчёт: `docs/production-check.json`, пояснения: [docs/STAGE-8.md](docs/STAGE-8.md). Проверка выполняется по локальному HTTP; публичный HTTPS-хостинг ещё не проверялся.

Обычный запуск с рабочей базой и настройками `.env`:

```sh
npm run build
npm start
```

По умолчанию: http://127.0.0.1:3000. Для развёртывания задайте `NODE_ENV=production`, `PUBLIC_ORIGIN` с точным HTTPS-адресом сайта, `HOST`, `PORT` и `DATABASE_PATH` на постоянном локальном диске. `TRUST_PROXY` меняйте только под известное число доверенных обратных прокси. Нужны один Node.js-процесс и HTTPS-прокси; SQLite не размещается на сетевой файловой системе или временном диске. База и резервные копии должны оставаться вне `dist/`.

Бронь сохраняется после перезапуска. Отмена меняет статус, а не удаляет запись. Токены хранятся только в виде хеша. Управляющая ссылка содержит секрет в URL-фрагменте; сохраните её после подтверждения. Письма и SMS не отправляются. Номера брони недостаточно для доступа.

Сервер формирует HTML из Nunjucks и текущего каталога базы, а ресурсы подключает через `dist/.vite/manifest.json`. На сервере нужны `server/`, `scripts/`, `shared/`, `src/pages/`, `src/partials/`, `src/scripts/services/dates.js`, файлы метаданных в `data/` и `dist/`. Одного `dist/` для работы недостаточно. Публикуется только содержимое, которое выдаёт `server/index.mjs`; корень проекта нельзя объявлять статическим каталогом. В production cookie входа требует HTTPS.

Для резервного копирования и восстановления подготовлены команды:

```sh
npm run backup:create
npm run backup:restore -- --from "storage/backups/ИМЯ_КОПИИ" --to "storage/restored-2026-10-20"
```

Копирование использует SQLite backup API и сохраняет фотографии со снимком базы, контрольными суммами и маркером завершения. Восстановление разрешено только в новый каталог; рабочая база не перезаписывается. Перед переключением путей остановите сайт и бота. Проверка копий: `npm run test:backup`. Полный порядок действий и сроки хранения: [docs/BACKUP.md](docs/BACKUP.md).

## Фотографии, cookie и согласия

Админка поддерживает собственные фотографии JPEG, PNG и WebP. Инструкция: [docs/ADMIN.md](docs/ADMIN.md). Sharp является production-зависимостью. Метаданные сохраняются в `media_uploads`, файлы WebP/AVIF — в `UPLOADS_DIR`, по умолчанию `storage/uploads`. Каталог должен находиться на постоянном диске вне `dist/`, сохраняться при каждом релизе и включаться в резервную копию вместе с SQLite. Загруженные файлы имеют неизменяемые имена и выдаются только по проверенному маршруту `/media/upload-…`.

Документы: `/privacy/`, `/consent/`, `/cookies/`. Единый источник текстов — `data/legal.json`. Скачиваемые PDF находятся в `public/documents/`, текстовые копии — в `docs/legal/`. Для обновления документов: изменить текст и версию → `npm run build` → `npm run legal:pdf` → `npm run build`. Команда PDF использует изолированную базу, не рабочие записи.

Форма записи требует три отдельные изначально снятые галочки: ознакомление с политикой, согласие на обработку и принятие правил. Без любой из них клиент не создаёт запрос, сервер также отказывает. В базе фиксируются версия и время. Уведомление о технических cookie не подменяет согласие на контакты; оно запоминается на 180 дней и повторно открывается из подвала. Рекламных cookie и аналитики нет.

По персональной ссылке посетитель может отозвать согласие и удалить контакты; будущая бронь при этом отменяется, места освобождаются. Плановая очистка контактов — через 90 дней после окончания занятия или отмены, при старте приложения и ежедневно в `npm start`. Техническая история без контактных полей остаётся в базе. Резервные копии и уже доставленные Telegram-сообщения этим действием не удаляются. Особенности и ограничения: [docs/LEGAL.md](docs/LEGAL.md).

Проверка: `npm run privacy:check`; отчёт `docs/privacy-media-check.json`, скриншоты `docs/screenshots/privacy-media/`.

Документы описывают демоверсию, а не выдуманного реального оператора. Для сбора настоящих данных нужно заполнить реквизиты оператора, канал обращений, условия хостинга и резервирования и оценить подключение Telegram. Публичное юридическое соответствие конкретного размещения здесь не подтверждается.

## Телефон и Telegram

Телефон +7 форматируется как `+7 (900) 000-00-00` и ограничен десятью цифрами после кода. Международные номера с другим кодом ограничены 15 цифрами. Сервер проверяет полный номер по тем же правилам, без обрезания некорректного запроса.

Для настоящего подтверждения в Telegram создайте бота через BotFather, задайте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` в `.env`, перезапустите сервер и запустите `npm run telegram:bot` в отдельном терминале. Пользователь получает сообщение после перехода из своей брони и нажатия «Старт». Без конфигурации сайт честно показывает, что бот ещё не подключён. Инструкция: [docs/TELEGRAM.md](docs/TELEGRAM.md).

`npm run notifications:check` проверяет маску и Telegram в Chrome с подменённым транспортом. Дополнительно 2026-10-19 проверена настоящая доставка через подключённого пользователем бота: сообщение получено, статус в базе — `sent`. При отсутствии запуска по ссылке доступна кнопка «Скопировать команду для бота».

## Демонстрационный характер

Адрес действующей мастерской, реальные контакты и отзывы не используются. Платёжных, почтовых, SMS- и картографических интеграций нет. Все 24 растровых сюжета сгенерированы встроенным image_gen, просмотрены и сохранены локально.

Эти команды готовят локальные файлы без повторной генерации. Шрифты и их лицензии хранятся в `src/assets/fonts/`.

Отчёт текущей версии: `docs/design-check-v2.json`; скриншоты: `docs/screenshots/stage-2-v2-*.png`. Для другого адреса используйте `PREVIEW_URL`, для установленного Edge — `BROWSER_CHANNEL=msedge`.


Скрипт самостоятельно запускает сервер с отдельной базой в памяти. Проверяет ширины 1920, 1440, 768, 390 и 360 px, создаёт 103 скриншота страниц и состояний, измеряет переполнения, размер текста полей, контраст основного текста и размещение элементов записи. Все 14 заголовков программ проверяются на каждом размере. Telegram в этом прогоне использует тестовую конфигурацию без отправки сообщений. Результаты и ограничения: [docs/STAGE-7.md](docs/STAGE-7.md), отчёт: `docs/visual-check.json`, снимки: `docs/screenshots/stage-7/`. Это проверка размеров окна настоящего Chrome, а не физических мобильных устройств.

При работающем `npm run dev`:

```sh
npm run pages:check
```

Скрипт проверяет каталог, URL и историю браузера, галереи и модальное окно, выбор участников и суммы, расписание, ошибки/повтор, занятые и прошедшие сеансы, отсутствие дат, прямые адреса и 404. Фикстуры состояния подменяют только HTTP-ответ в тестовом браузере и не меняют рабочую базу. Четыре основные страницы проверяются на 1440, 768, 390 и 360 px. Отчёт: `docs/pages-check.json`; скриншоты: `docs/screenshots/stage-3/`.

Для метаданных опубликованных ссылок задайте `PUBLIC_ORIGIN` с окончательным адресом сайта до сборки: canonical, og:url и og:image станут абсолютными. Пока домен не задан, сторонний адрес не подставляется. Демоверсия помечена `noindex`.
