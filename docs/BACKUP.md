# Резервные копии и восстановление

Для **опубликованной версии Vercel** используйте `npm run cloud:backup` и порядок из [CLOUD.md](CLOUD.md). Команды ниже относятся к локальной файловой SQLite; `backup:restore` восстанавливает облачную копию только в новый локальный каталог и не перезаписывает Turso.

Команды запускаются из корня проекта. Они читают `.env`. Копия содержит контакты демонстрационных записей, хеши пароля и персональных ссылок: храните её закрытой, как рабочую базу. В этой передаче рабочие контакты в копию не выгружались; проверка выполнена на временных данных.

## Создать копию

```sh
npm run backup:create
```

Используются `DATABASE_PATH`, `UPLOADS_DIR` и `BACKUP_DIR` из `.env`. По умолчанию это `storage/ladno.sqlite`, `storage/uploads`, `storage/backups`. Каждый запуск создаёт отдельный каталог `ladno-<время>-<случайный суффикс>`:

```text
manifest.json
ladno.sqlite
uploads/
```

Команда использует SQLite backup API, поэтому сайт и бот можно оставить работающими. После согласованного снимка базы копируются все файлы фотографий, перечисленные в его медиатеке. Файлы изображений неизменяемы и появляются до добавления записи в базу. Новые загрузки после снимка попадут в следующую копию. Файлы без записи в медиатеке не включаются.

Проверяются целостность SQLite и внешние ключи, записываются SHA-256 базы и каждой фотографии. `manifest.json` создаётся последним. Каталог без него — незавершённая копия, использовать его нельзя. Контрольные суммы обнаруживают повреждение, но не доказывают подлинность чужой копии. Восстанавливайте только свои доверенные копии.

Это согласованный снимок базы и загруженных фото, а не архив приложения: отдельно сохраняйте соответствующую версию исходников, lock-файл, исходные сгенерированные изображения, PDF и защищённые настройки сервера. `.env`, токен Telegram и файл пароля не включаются в копию. Не отправляйте их в публичное хранилище.

## Восстановить без перезаписи

```sh
npm run backup:restore -- --from "storage/backups/ИМЯ_КОПИИ" --to "storage/restored-2026-10-20"
```

Назначение должно отсутствовать; его родитель должен существовать. Команда отклоняет существующий каталог, повреждённые файлы, небезопасные имена и неподдерживаемую новую схему базы. Рабочую базу и пути `.env` она не меняет. При нехватке места может остаться неполный новый каталог: не подключайте его, повторите в другой новый каталог после устранения причины.

Порядок переключения:

1. Создайте свежую копию текущей базы, если она ещё доступна. Сохраните её отдельно.
2. Остановите сайт и **обработчик Telegram**, включая локальный Vite, если он использует эту же базу. Не принимайте новые записи во время переключения.
3. Выполните восстановление в новый каталог. Оно проверяет файлы до копирования, применяет поддерживаемые миграции, очищает контакты с истёкшим 90-дневным сроком, отзывает все старые сеансы входа хозяйки. Неоконченные Telegram-запросы переводятся в `unknown`, чтобы не отправить повторное подтверждение.
4. Сверьте дату копии, расписание, суммы и новые записи после её создания. Копия не содержит последующих изменений. Отмены и отзывы согласий, выполненные после её даты, нужно повторно применить **до открытия доступа**; автоматического внешнего журнала отзывов нет. Не используйте восстановление для возврата удалённых контактов.
5. В `.env` задайте `DATABASE_PATH=storage/restored-2026-10-20/ladno.sqlite` и `UPLOADS_DIR=storage/restored-2026-10-20/uploads` (или абсолютные пути). На Linux при systemd измените оба пути в `/etc/ladno.env`; каталог должен оставаться внутри разрешённого `/var/lib/ladno`.
6. Запустите сайт, проверьте каталог и фото, войдите в админку и сверяйте записи. Пароль владельца соответствует копии; если он утерян, используйте `npm run admin:setup -- --reset` с новыми путями. Затем запустите одного бота. Старые персональные ссылки брони работают, если сама бронь присутствовала в копии.
7. Только после проверки возобновите приём записей. Старый рабочий каталог оставьте закрытым до окончания проверки, затем удалите по правилам хранения.

На сервере `.env` и `/etc/ladno.env` не должны противоречить друг другу: установленные переменные процесса имеют приоритет над файлом, который читает npm-команда. Для команд обслуживания используйте ту же конфигурацию, что для работающего сайта.

## Регулярность и место хранения

Для небольшого проекта подготовлен пример ежедневного systemd-таймера на 03:15 по Москве: `deploy/ladno-backup.*`. Он включается администратором только при развёртывании. На текущем компьютере таймер не установлен.

Копия на том же диске защищает от ошибочного изменения, но не от потери диска. Переносите завершённые каталоги в закрытое зашифрованное хранилище на другом носителе; ключ шифрования храните отдельно. Ограничьте срок резервных копий, например семью днями для демонстрационного проекта, и контролируйте свободное место. Автоматическое шифрование, перенос, удаление старых копий и уведомление о сбоях не подключены. Скрипт намеренно ничего не удаляет. При удалении копий учитывайте и удалённое хранилище.

Периодически проверяйте восстановление в изолированный каталог. Автоматическая проверка:

```sh
npm run test:backup
```

Она проверяет работающую WAL-базу, реальные CLI-команды, шесть вариантов фотографии, сумму и места, персональную ссылку, повтор запроса, повтор отмены, защиту от перезаписи и повреждения, очистку старых контактов и отзыв входов. Рабочая база не участвует.

Основа решения: [официальная документация SQLite Online Backup API](https://www.sqlite.org/backup.html).
