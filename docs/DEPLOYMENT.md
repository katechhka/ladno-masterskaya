# Развёртывание «Ладно»

**Текущее размещение — Vercel:** https://ladno-masterskaya.vercel.app/. Используйте [CLOUD.md](CLOUD.md). Ниже сохранён прежний вариант самостоятельного Linux-сервера; он не устанавливался и не используется опубликованной версией.

Выбран один вариант: Linux-сервер с systemd, Nginx перед Node.js и постоянным локальным диском. Один процесс сайта, при включённом Telegram — ещё один процесс бота. База SQLite и загруженные фотографии остаются вне каталога релиза. Статический хостинг, временный диск serverless и несколько реплик сайта с общей сетевой SQLite для этого проекта не подходят.

Публичное размещение не выполнялось. Шаблоны ниже подготовлены для настройки администратором; на настоящем Linux-сервере команды и службы ещё не запускались. Локально проверена эквивалентная схема HTTPS-прокси → production Node.js → файловая SQLite, включая вход хозяйки и перезапуск.

## Размещение файлов

```text
/srv/ladno/app/                исходники, node_modules и dist
/srv/ladno/app/.env            закрытая ссылка на /etc/ladno.env
/etc/ladno.env                настройки, владелец root, группа ladno, права 0640
/var/lib/ladno/ladno.sqlite    постоянная база
/var/lib/ladno/uploads/       собственные фотографии
/var/lib/ladno/backups/       закрытые копии
```

Создайте системного пользователя и группу `ladno`, существующие каталоги с доступом этой группы и права 0700 для `/var/lib/ladno`. У пользователя должен быть доступ на чтение исходников и запись постоянных данных. Для первоначальной установки и сборки ему также нужен доступ на запись в `/srv/ladno/app`; запущенные службы ограничивают запись каталогом `/var/lib/ladno`. Установите совместимый Node.js: ветка 22 начиная с 22.12 или 24; текущие проверки выполнены на 22.21.0. Уточните настоящий путь к `node` командой `command -v node` и исправьте `/usr/bin/node` в службах, если он другой. Не переносите Windows `node_modules` на Linux: установите зависимости на сервере.

Перенесите исходники вместе с `package-lock.json`, `public/`, `data/`, `src/`, `server/`, `shared/`, `scripts/` и `deploy/`. Не переносите `.cache`, старые `node_modules`, `.env` или `storage/admin-access.txt` в публичный архив. Для работающего сервера нужны Nunjucks-шаблоны и данные; одного `dist/` недостаточно. Рабочие SQLite и фото переносятся отдельно через согласованную резервную копию, а не обычным копированием открытой WAL-базы.

## Настройки

Создайте `/etc/ladno.env` на основе `.env.example`. Здесь `workshop.example` — только пример; замените его выбранным доменом:

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=3000
PUBLIC_ORIGIN=https://workshop.example
TRUST_PROXY=1
DATABASE_PATH=/var/lib/ladno/ladno.sqlite
UPLOADS_DIR=/var/lib/ladno/uploads
BACKUP_DIR=/var/lib/ladno/backups
TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_USERNAME=
TELEGRAM_PROXY_URL=
```

Создайте закрытую символическую ссылку `/srv/ladno/app/.env` на `/etc/ladno.env`: это позволяет npm-командам и systemd читать одну конфигурацию. Не публикуйте `.env`, не задавайте секретам префикс `VITE_`. Если Telegram нужен, внесите токен своего отдельного бота и username без `@`. Они не входят в frontend-сборку.

`PUBLIC_ORIGIN` должен точно совпадать с HTTPS-адресом сайта без дополнительного пути. `TRUST_PROXY=1` соответствует **одному** Nginx и недоступному снаружи Node.js на 127.0.0.1. Если добавится CDN или балансировщик, заново настройте доверенные прокси и проверку Origin. Не открывайте порт 3000 в интернет.

## Первая установка

В `/srv/ladno/app` от имени пользователя `ladno`:

```sh
npm ci
npm run db:seed
npm run admin:setup
npm run build
```

Для установки и сборки нужны dev-зависимости Vite и Stylus: не используйте `npm ci --omit=dev` на этом шаге и проверьте, что `NODE_ENV` окружения оболочки не исключает их. При необходимости используйте `npm ci --include=dev`. Отдельный процесс Chrome нужен только тестам и пересозданию PDF, для обычной работы сайта он не требуется. Готовые PDF уже включены.

Если переносите существующую мастерскую, сначала восстановите копию и задайте восстановленные пути. Повторное `db:seed` не удаляет записи и не заменяет правки хозяйки, но начальное расписание не продлевается автоматически: новые даты добавляйте в админке. Кнопки сброса рабочих данных нет; для нового чистого демо используйте отдельную новую базу и каталог фотографий, сохранив прежние данные.

При создании владельца пароль записывается в закрытый `/srv/ladno/app/storage/admin-access.txt`. Сохраните его в менеджере паролей и удалите файл. Не выводите пароль в журналы и не включайте файл в релиз. В существующей базе прежний пароль сохраняется.

## HTTPS и процессы

1. Настройте DNS своего домена и действующий доверенный сертификат, включая его автоматическое продление. Это не выполняется приложением.
2. Адаптируйте `deploy/nginx.conf.example`: домен и пути сертификатов. Все маршруты проходят через Node.js, корень проекта не используется как Nginx `root`. Предел запроса 11 МБ пропускает допустимые фотографии до 10 МБ. Заголовки прокси перезаписываются значениями Nginx.
3. Скопируйте `deploy/ladno.service` в `/etc/systemd/system/`. Если Telegram настроен, добавьте `ladno-telegram.service`. Обе службы читают один `/etc/ladno.env`, используют одну базу. Запускайте ровно одного обработчика на бота.
4. Проверьте конфигурации и включите службы:

```sh
sudo nginx -t
sudo systemd-analyze verify /etc/systemd/system/ladno.service
sudo systemctl daemon-reload
sudo systemctl enable --now ladno.service
sudo systemctl reload nginx
# Только при настроенном боте:
sudo systemctl enable --now ladno-telegram.service
```

Службы запускают Node.js напрямую, получают SIGTERM и перезапускаются при сбое. Не запускайте параллельно `npm start` с теми же портом и базой. Telegram использует исходящее HTTPS long polling; публичный webhook не нужен. При переносе с этого компьютера остановите локального обработчика перед запуском серверного. Открытие чата и нажатие «Старт» остаются действием посетителя.

## Проверка публикации

Откройте HTTPS-адрес и внутренние страницы напрямую: каталог, детальную программу, расписание, документы, неизвестный адрес (должен вернуть 404). Проверьте обложки и собственное загруженное фото, мобильную ширину 360 px, вход/выход хозяйки. Cookie входа должна быть Secure и HttpOnly.

Оформите бронь только с вымышленными данными: один участник и группа; проверьте итоговую сумму, сохранение после перезапуска и отмену. Если Telegram включён, проверьте доставку в личный чат. Нельзя считать сообщение отправленным без ответа провайдера. На публичном адресе дополнительно проверьте закрытый доступ к `.env`, SQLite, резервным копиям и файлу пароля; корень проекта не должен выдаваться статически.

Смотрите `systemctl status ladno` и `journalctl -u ladno --since today` без публикации журналов. Не включайте логирование тел запросов, Cookie и Authorization. Шаблон Nginx отключает access log; error log ограничен критическими событиями. Если хостинг добавляет собственные журналы, согласуйте их состав и срок хранения. Следите за местом на диске и неуспешными копиями; внешнее оповещение о сбоях не подключено.

## Копии и обновления

Подробности: [BACKUP.md](BACKUP.md). Для ежедневных копий установите `deploy/ladno-backup.service` и `.timer`, затем:

```sh
sudo systemd-analyze verify /etc/systemd/system/ladno-backup.service /etc/systemd/system/ladno-backup.timer
sudo systemctl daemon-reload
sudo systemctl start ladno-backup.service
sudo systemctl enable --now ladno-backup.timer
sudo systemctl list-timers ladno-backup.timer
```

Проверьте завершённый каталог с manifest.json и пробное восстановление. Таймер создаёт копии, но не шифрует, не переносит на другой диск и не удаляет старые. Настройте эти действия и ограничьте срок хранения отдельно. Доступ службы разрешён `/var/lib/ladno`; при изменении места копий адаптируйте `ReadWritePaths`.

Перед новым релизом создайте копию, остановите сайт и бота, обновите исходники и lock-файл, выполните `npm ci --include=dev`, `npm run db:migrate`, `npm run build`, запустите службы и проверьте запись. Не заменяйте `/var/lib/ladno` при обновлении кода. Миграции только вперёд: откат кода после несовместимой миграции требует соответствующей старой версии и восстановления её копии в новый каталог. Такое восстановление теряет изменения после даты копии, поэтому сначала сохраните текущее состояние и сверяйте записи вручную.

## Границы демонстрации

Сайт отмечен как демопроект и `noindex`. Не придумывайте реквизиты действующей организации. До реального приёма посетителей необходимо заменить демонстрационные сведения и подготовить документы для конкретного оператора; условия и незавершённые вопросы перечислены в [LEGAL.md](LEGAL.md). Наличие галочек и PDF само по себе не подтверждает готовность к сбору реальных данных.

Первичные источники конфигурации: [Nginx proxy_set_header](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header), [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html). Фактическая установка Nginx/systemd и доверенного сертификата на выбранном сервере ещё требует проверки.
