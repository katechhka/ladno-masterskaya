# Этап 8 — проверка production-запуска

20 октября 2026 года проверен собранный сайт с настоящим `server/index.mjs` в отдельном процессе Node.js. Установлены `NODE_ENV=production`, точный `PUBLIC_ORIGIN`, `TRUST_PROXY=0`; ограничения API и production-заголовки включены.

## Воспроизведение

```sh
npm run build
npm run production:check
```

Проверка создаёт временную файловую SQLite-базу внутри `.cache/tests/production-*`, наполняет её относительно текущей московской даты, запускает и перезапускает сервер. После завершения процесс и тестовая база удаляются. Рабочая база и настройки `.env` не меняются. Telegram отключён только в тестовом процессе; настоящих сообщений нет.

Отчёт: [production-check.json](production-check.json). Четыре снимка подтверждения и отмены: `screenshots/stage-8/`.

## Что проверено

- Все 22 адреса страниц, включая 14 программ, открываются напрямую и отдают собранный HTML. Есть заголовки и описания страниц; пользовательские страницы содержат Open Graph. Техническая страница `/design/` не предназначена для публикации ссылки.
- Переход `/master-classes?category=ceramics` ведёт на адрес со слешем, сохраняя параметры.
- Неизвестный маршрут возвращает оформленную страницу с HTTP-кодом 404. Запросы к `.env`, базе, серверным файлам и исходным шаблонам тоже получают 404.
- Файлы сборки не ссылаются на исходные модули Vite. В `dist` нет баз данных, `.env`, маркеров приватных ключей и Telegram API-токенов.
- Включены CSP, HSTS, запрет встраивания, `nosniff` и `no-referrer`. Изменение записи с чужого Origin отвергается. Ответы API и страниц записи не кешируются.
- В настоящем Chrome на 1440×1000 и 360×800 пройден сценарий: открытие основных страниц → обязательный телефон и согласия → проверка → запись двух участников → подтверждение.
- Сумма проверена по SQLite и серверной цене. Остаток уменьшился ровно на два места.
- После остановки процесса и нового запуска сохранены бронь и её персональная ссылка. Номер брони и запрос без токена не открывают контакты.
- Отмена с подтверждением возвращает места; повторная отмена не меняет остаток. Отменённые записи сохраняются при следующем перезапуске.
- Действующий ограничитель возвращает 429 и `Retry-After` после превышения числа действий.
- В браузерном прогоне нет ошибок JavaScript, ошибок консоли, нарушений CSP и неудачных загрузок ресурсов. Тестовые телефон, email и токен не появляются в журнале серверного процесса.

## Исправление теста

Полный прогон выявил зависимость проверки прошедшего сеанса от дня недели: в понедельник и вторник мастерская отдыхает, поэтому наполнение не обязано иметь вчерашний сеанс. Тест теперь сам создаёт заведомо прошедший сеанс относительно текущего времени. Поведение рабочего расписания не изменено.

Повторный `npm run test:all` включает сборку, 39 серверных тестов, браузерные проверки бронирования, пограничных случаев и телефона/Telegram. Итог записывается в [automated-check.json](automated-check.json).

## Границы проверки

Это локальная проверка production-режима по HTTP на loopback-адресе. Публичное развёртывание, реальный домен, сертификат HTTPS, настройки внешнего reverse proxy и автоматический запуск после перезагрузки хостинга не выполнялись. Перед публикацией нужен постоянный диск для SQLite, точный HTTPS `PUBLIC_ORIGIN` и проверка на выбранном сервере. Установка HSTS проверена как HTTP-заголовок, не как работа TLS.

Во время этого этапа пользователь запросил управление мастерской через админку. Состав следующего этапа описан в [ADMIN-PLAN.md](ADMIN-PLAN.md). После внедрения админки production-проверку необходимо расширить и повторить: текущий результат относится к версии сайта до её появления.
