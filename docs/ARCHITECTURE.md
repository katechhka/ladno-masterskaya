# Архитектура

Публикация Vercel добавляет асинхронный адаптер Turso и Vercel Blob: [CLOUD.md](CLOUD.md). Общие сервисы работают через `server/db/flow.mjs`: синхронные результаты локальной SQLite возвращаются сразу, обещания облачного адаптера возобновляют ту же операцию. В Express и HTML-renderer результаты ожидаются через await. Локальные транзакции остались синхронными, удалённые используют выделенную write-транзакцию и AsyncLocalStorage. Программная логика цены, мест, дублей и отмены не дублируется между окружениями.

## Источники данных

С этапа 9 единственный рабочий источник программ — таблица `workshop_programs` в SQLite. Она хранит данные программы, галерею, признак архива и версию для защиты от устаревшего сохранения. `data/workshops.json` и `galleries.json` используются один раз для начального импорта. Метка `catalog_imported` не даёт повторному запуску перезаписать правки хозяйки. `teachers.json` — преподаватели; `site.json` — направления, тексты, FAQ, правила и описание демонстрационных данных.

Модуль `server/services/catalog.mjs` проверяет исходное наполнение; `catalog-store.mjs` читает рабочий каталог, `admin.mjs` валидирует правки и связи. Vite собирает HTML-основу и ресурсы в `dist/`, включая manifest. В разработке и production HTML-страницы формируются Nunjucks из базы при запросе через `server/render.mjs` и общую функцию `renderDocuments`. Прежние полноценные адреса страниц сохранены. Шапка и подвал подключаются из `src/partials/`.

Цены и описания меняются из `/admin/` без пересборки. Публичные страницы, API и расчёт записи читают один каталог из базы. Старые брони сохраняют цену в копейках на момент записи. Длительность и вместимость уже созданных сеансов сохраняются, пока хозяйка не изменит конкретный сеанс. Архивированная программа скрыта с публичных страниц и закрыта для новых броней, но доступна для истории существующих записей.

24 изображения сгенерированы и сохранены локально. Программы ссылаются на идентификаторы в `data/images.json`; состав галерей — `data/galleries.json`. Исходники и полные промпты сохранены, стоки и картинки из поиска не используются. Городские мотивы в визуалах иллюстративны.

По дополнительному запросу пользователя разрешены собственные фотографии хозяйки. `media_uploads` содержит их метаданные, `readMedia(db)` объединяет их с исходной сгенерированной медиатекой. Файлы лежат в постоянном `UPLOADS_DIR`, вне сборки. Сервер проверяет авторизацию, CSRF/Origin, сигнатуру, размер и декодирование, перекодирует в WebP/AVIF без EXIF и выдаёт только безопасные производные по строгому имени. Для обработки Sharp входит в production-зависимости. Галереи новых программ хранятся в том же рабочем каталоге SQLite.

## База

С этапа 4 интерфейс использует актуальные `/api/catalog` и `/api/sessions`. `server/services/bookings.mjs` читает сеансы и сумму подтверждённых мест из SQLite. Контакты и секреты публичный запрос не выбирает. Клиентский модуль данных общий для главной, расписания, детальной страницы и записи. `public-data.mjs` сохраняет служебный статический снимок для экспорта, но интерфейс не использует его как источник доступности.

Каталог фильтруется на клиенте по атрибутам карточек, созданным из рабочей базы, с сохранением состояния в URL. Скрипты страниц подключаются ES-модулями по виду страницы. Галереи используют общий компонент jQuery, нативный dialog, стрелки, миниатюры и жесты. Полноценная шапка, подвал, метаданные и каркас страниц находятся в общих шаблонах Nunjucks.

Vite работает в MPA-режиме. Middleware нормализует завершающий слеш и возвращает оформленную 404 только для неизвестных адресов страниц. Watcher реагирует на исходные данные и шаблоны, не на экспортированные JSON, чтобы не создавать цикл пересборки.

`sessions`: конкретная дата UTC, окончание, вместимость, статус и ID программы. Все пользовательские даты отображаются в Europe/Moscow. В SQLite сравниваются нормализованные ISO UTC строки.

`bookings`: количество участников, снимок цены, сумма в копейках, контакты, версия согласия, статус, хеш секретного токена. Номер брони и токен управления — разные сущности. Ни номера, ни токены не должны давать доступ к спискам участников.

`idempotency_keys`: уникальный ключ клиента, хеш нормализованного тела запроса и связанная бронь. Повтор с тем же телом возвращает ту же бронь; другое тело с тем же ключом отклоняется.

Остаток мест вычисляется как вместимость минус сумма участников подтверждённых броней. Отдельного изменяемого счётчика свободных мест нет. SQL-триггеры дополнительно блокируют превышение вместимости и её уменьшение ниже занятого количества.

Создание брони и запись ключа повторного запроса выполняются одной `BEGIN IMMEDIATE`-транзакцией. Транзакции, дата сеанса, серверная цена, проверка токена и лимиты запросов дополняют ограничения схемы. Контакты проверяются Zod, телефон обязателен. Отмена по токену также транзакционна и идемпотентна.

`server/app.mjs` подключает API к Vite в разработке и preview. `server/index.mjs` обслуживает production-сборку и API. API запрещает кеширование и изменения с чужого Origin, ограничивает размер JSON и частоту запросов. В production Helmet задаёт CSP для локальных ресурсов. Секретный токен создаётся браузерным Web Crypto (256 бит), сохраняется в базе как SHA-256 и передаётся API в Authorization. URL-фрагмент не попадает в HTTP-адрес и Referer. Контакты и токены не логируются; публичных методов просмотра по номеру брони нет.

## Наполнение

Первая команда `db:seed` фиксирует московскую календарную дату в `app_metadata`. Генерируется шесть недель занятий со среды по воскресенье и прошедший сеанс для проверки состояния. В выходные два занятия, в остальные рабочие дни мастерской одно. Программы чередуются, занятий одновременно нет.

ID исходного демонстрационного сеанса детерминирован по программе и дате. Повторный seed использует исходную опорную дату и `INSERT OR IGNORE`: не переносит занятия и не удаляет брони. Новые сеансы и серии создаются хозяйкой в админке, идентификаторы — случайные UUID. Общего автоматического сброса рабочей базы нет. Закрытые и заполненные сеансы для QA создаются только в изолированных тестовых базах.

## Развёртывание

Документы и согласия описаны в [LEGAL.md](LEGAL.md). Политика, отдельное согласие и cookie формируются из `data/legal.json`; PDF и Markdown получаются из того же текста. Клиент и сервер требуют три отдельных подтверждения перед новой бронью. Версия фиксируется в `consent_version`, время — в `consent_at`. Cookie-уведомление хранит только версию ознакомления и не заменяет согласия в форме.

`privacy.mjs` удаляет контактные поля и привязку Telegram по отзыву или спустя 90 дней после окончания/отмены. Метка `data_erased_at` отличает удалённые контакты от настоящих значений. Для будущей брони отзыв также отменяет запись и освобождает места в одной транзакции. Техническая история сохраняется; удаление резервных копий не заявляется. Очистка выполняется на старте приложения, в обычном серверном процессе — также раз в сутки.

Один HTTP-процесс Node.js и отдельный необязательный обработчик Telegram, SQLite на постоянном локальном диске, HTTPS через обратный прокси. Статические файлы находятся в `dist`, база и её WAL/SHM — за пределами публичного каталога. Для нескольких HTTP-реплик и сетевой файловой системы эта схема не предназначена.

Telegram подключается по запросу пользователя после записи: сервер выдаёт отдельный одноразовый токен на 15 минут, пользователь открывает личный чат бота. Таблица `telegram_confirmations` хранит хеш токена, статус, chat_id и message_id. Обработчик long polling сохраняет offset и присваивает отправку транзакционно. Неизвестный результат не повторяется автоматически. Секрет бота находится только в `.env`; в клиентский код он не передаётся. Инструкция: [TELEGRAM.md](TELEGRAM.md).

Резервная копия должна быть согласованным снимком через SQLite backup API: копирование только `.sqlite` во время записи без учёта WAL ненадёжно. Команда резервного копирования и инструкция восстановления будут добавлены до передачи проекта.
